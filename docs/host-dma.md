# 主機 DMA（$E90020／$E90030）（a，Bcan 反編譯＋自製卡帶量測）

日期：2026-09-02。證據等級 `confirmed-Bcan`：語意取自 Bcan 0.0.8b 的
`sub_1400A31A0`，數值行為由自製卡帶 `homebrew/dmaprobe/` 逐 byte 驗證。
**硬體真相仍待實機訊號。**

## 1. 暫存器

每通道六個 word，通道 0 在 `$E90020`、通道 1 在 `$E90030`：

| 位移 | 內容 |
|---|---|
| `+0` / `+2` | source 位址 高／低 word |
| `+4` / `+6` | destination 位址 高／低 word |
| `+8` | count |
| `+10` | control，**寫入即觸發** |

搬移的單位數是 `count + 1`。位址在使用時都遮成 24 bit。

兩個通道的**暫存器檔是分開的**：把通道 1 設定好但不觸發，改用通道 0 搬一次，再單獨寫
通道 1 的 control，通道 1 用的仍是自己先前存下的位址與 count（量測見 §4）。

## 2. control 位元

| 位元 | 作用 |
|---|---|
| 15、11 | 觸發：`control & $8800` 不為 0 才動作 |
| 12 | 1 ＝ word 傳輸（步進 ±2），0 ＝ byte（步進 ±1）|
| 10 | destination 遞減 |
| 9 | source 遞減 |
| 8 | word 模式下，步進後若 destination 落在 16 byte 邊界就再減 16 |
| 其餘 | 量測範圍內沒有效果（`$8801`、`$9808` 與 `$8800`、`$9800` 結果相同）|

`control` 為 **`$A800`**（完全相等，不是位元判斷）時走另一條路：destination 若在
VRAM（`$F4xxxx`）就寫入 word 0 並把 destination 步進 ±2，**不推進 source**；
否則從 `source + (destination & 1)` 讀一個 byte 寫過去。這條分支在 MAME 也是以
相等比對寫成的，看起來是為某一款軟體的行為留的特例，**不是通則**。

非零但不含觸發位元的 control（例如 `$0001`）**不會被寫入暫存器**，Bcan 直接回傳
錯誤碼 12。寫入 0 則正常存進暫存器。

實測這個錯誤碼會讓 Bcan **停止整個工作階段**：同一顆映像只把最後一個案例的 control
從 `$8800` 換成 `$0001`，前者跑完並照常截圖，後者的視窗回到未載入 ROM 的灰底、
F8 產不出檔案，而且沒有留下 `*.fault.txt`。正對照排除了「第 13 個案例本身讓版面出錯」
這個解釋。本專案的重製不會停機，只是不觸發搬移。

## 3. 傳輸結束後的狀態

source、destination 會被寫回**推進後的值**，count 不變，control 存入寫入值。
傳輸中途發生匯流排錯誤時整組暫存器都不寫回，維持觸發前的值。

Bcan 允許 DMA 觸發巢狀最多 8 層（第 9 層回錯誤碼 12），不是完全禁止重入。

## 4. 量測

`homebrew/dmaprobe/` 的映像對每個 control 值做一次搬移：目的區先填成索引 255，
起點在自己 256 byte 區塊的正中央（因此遞減方向也不會踩到隔壁），搬完再把六個 DMA
暫存器讀回另一塊 VRAM。畫面用 8bpp tilemap 顯示這兩塊，一個 byte 就是一個像素。

12 個案例在 Bcan 0.0.8b 與本專案 Linux 重製上的**搬移結果完全相同**：

| control | 變動 byte 數 | 相對區塊起點的位移 | 讀出的語意 |
|---|---:|---|---|
| `$8800` | 16 | 128–143 | byte，兩端遞增 |
| `$9800` | 32 | 128–159 | word |
| `$8C00` | 16 | 113–128 | destination 遞減 |
| `$8A00` | 16 | 128–143 | source 遞減（目的不變）|
| `$9C00` | 32 | 98–129 | word ＋ destination 遞減 |
| `$9A00` | 32 | 128–159 | word ＋ source 遞減 |
| `$9900` | 16 | 128–143 | bit8 讓 destination 每 16 byte 退回，只用掉 16 byte |
| `$A800` | 32 | 128–159 | 目的在 VRAM，寫入的是 0 |
| `$8000` | 16 | 128–143 | 單獨 bit15 就能觸發 |
| `$0800` | 16 | 128–143 | 單獨 bit11 也能觸發 |
| `$8801` | 16 | 128–143 | 低位元無效果 |
| `$9808` | 32 | 128–159 | 同上 |

### 4.1 通道 1

同一組 12 個案例改跑在 `$E90030`，畫面與通道 0 的版本**逐像素相同**（Bcan 與本專案
各自比對都是 0 個像素差）。通道 1 沒有任何自己的特殊行為。

### 4.2 兩個通道的暫存器檔是分開的

三個案例的序列：通道 1 設好目的區 0、`count = 15`，control 寫 0（不觸發）；通道 0 搬 8 個
byte 到目的區 1；最後**只寫**通道 1 的 control。結果是目的區 0 出現 16 個 byte、目的區 1
是 8 個、第三個案例自己的目的區沒有變動——第三步用的是通道 1 先前存下的位址與 count。
若兩個通道共用暫存器檔，第三步會搬到目的區 1。Bcan 與本專案的結果相同。

## 5. 一處已知差異：暫存器回讀

同一顆映像把六個 DMA 暫存器讀回畫面時，**Bcan 一律回 0**；本專案回的是推進後的
實際值。Bcan 的讀取分派器對 `$E90020–$E9003F` 沒有任何 case，屬未實作而非刻意行為。
兩邊逐像素比對時，整張畫面的差異就只有回讀那一欄（168 個像素，含 tilemap wrap 的複本），
搬移結果本身完全相同。

硬體真相 **待查證**。本專案保留實際值：DMA 控制器讓 CPU 讀回進度是常見設計，
而「一律回 0」只在模擬器層面成立。本地九款映像沒有一款讀這段位址，兩種選擇目前
都不影響任何已知軟體。

## 6. 時序

搬移**要花多久、期間 CPU 能不能跑**，是這一段唯一還沒有量測的部分。以下把「已知」與
「只是參考」分開列，避免把類比當成證據。

### 6.1 板級可確認的部分（p）

`APU.sch` 顯示 UM6619 接到 68000 的 `BR/BG/BGACK`（見
[hardware-evidence-method.md](hardware-evidence-method.md) §3.1）。這三條線就是 68000 的
**三線匯流排仲裁協定**，所以 DMA 不是「旁路搬移」，而是向 CPU 要走匯流排的 bus master：
搬移期間 CPU 拿不到匯流排。這一點不需要類比就成立。

搬移的來源與目的都是一般匯流排位址（量測過 ROM → VRAM），所以每個單位至少要一次讀
週期加一次寫週期——**兩個匯流排週期**，中間經過控制器內部的暫存。

### 6.2 兩個模擬器都沒有模型（a／b）

- **Bcan**：在寫入 control 的當下把整段搬完，CPU 不損失任何週期。
- **MAME**（`src/mame/umc/supracan.cpp`，commit `6ae579a`）：同樣是當下搬完，但原始碼
  留了一行**被註解掉**的 `spin_until_time(count * 2)`，上面寫著
  `TODO: are these DMA cycle steal? There's no indication of a DMA status read so far that
  would indicate burst.`

也就是說兩個 oracle 在這一項上都不能當依據，而且 MAME 明說它沒看到任何軟體讀 DMA
狀態。本庫的量測與此一致：Bcan 對 `$E90020–$E9003F` 的讀取一律回 0，本地九款在開機到
待機的段落仍然正常。這不足以證明整個遊戲流程都不讀，但目前沒有反例——**沒有已知軟體
會因為時序模型不同而表現不同**。

### 6.3 近似規格參考：MC68450 DMAC（c）

UM6619 是 UMC 的自製 ASIC，沒有公開規格書。同一條匯流排上有原廠文件可查的 DMA 控制器
是 Motorola 自己的 **MC68450**（[datasheet, Jul 1989](https://www.bitsavers.org/components/motorola/68000/MC68450_Direct_Memory_Access_Controller_DMAC_Jul89.pdf)）。
它不能證明 UM6619 怎麼做，但它界定了「在 68000 匯流排上做 DMA」的成本結構與可能的模式：

| MC68450 的規定 | 出處 | 對 A'Can 的意義 |
|---|---|---|
| dual-address 傳輸：來源先進控制器內部暫存，第二個匯流排週期才寫到目的 | §1.2 Operand Transfer Modes、Figure 1-4 | 記憶體到記憶體必然是每單位兩個週期，與 §6.1 的推論一致 |
| 「所有讀週期以四個時脈計、寫週期以五個時脈計」 | Figure 4-25 的註 2 | 每個單位約 9 個時脈的量級 |
| back-end overhead 最佳情況兩個時脈；另有 front-end 與 inter-cycle overhead | §4.5.2.2、Figure 4-23／4-24 | 每次取得匯流排都有固定成本，不只是搬移本身 |
| 模式分 burst、cycle steal、cycle steal with hold | §5.2.3.3.3–5.2.3.3.5 | 這是設計空間；**A'Can 用哪一種未知** |

把「每單位九個時脈」套在已定案的 68k 時脈 10.738635 MHz 上：一個單位約 **838 ns**，
本庫探針那種 16 單位的搬移約 **13 µs**，而填滿 32 KiB 的 byte 搬移約 **27 ms**——
超過一個 60 Hz 幀。這說明時序模型不是純粹的潔癖：大批搬移在實機上不可能是瞬間完成，
把它當成瞬間會讓「DMA 期間的畫面狀態」與實機不同。

⚠ 上表是**參考框架不是證據**。MC68450 是外接控制器，UM6619 是把 DMA 做進系統控制器
裡的自製晶片，週期數、overhead 與模式都可能不同。本庫不把這些數字寫成 A'Can 的規格。

### 6.4 要怎麼收斂

- **實機量測**：用計數器 `$E90014/16`（輸入時脈 master/12 ＝ 8.9488625 MHz，見
  [memory-map.md](memory-map.md) §2.2）在觸發前後各讀一次，量一次大批搬移的實際耗時，
  再除以單位數。這需要實機或一台已經被證實時序正確的模擬器，現有手段做不到。
- **找到相依的軟體**：目前沒有任何一款會因為時序不同而表現不同；出現這種案例時，
  它本身就是判準。

在那之前，本專案與 Bcan、MAME 一樣採「觸發即完成」，並在此標記為**已知的簡化**，
不是已驗證的行為。

## 7. 其他尚未量到的

- **8 通道之說**：外界流傳的 8 組 DMA 沒有在 Bcan 或 MAME 找到對應，維持待查證。
- **匯流排錯誤的實機行為**：Bcan 在傳輸中途遇錯就整組暫存器不寫回，實機是否如此未知。
