# 從執行檔追出一個暫存器的資料流：方法與三個會產生自洽錯誤的陷阱

本文用一個實際案例說明「某個硬體暫存器位元有沒有被某支模擬器消費」該怎麼查，以及查的
過程中三次得到「看起來自洽、其實錯誤」結論的成因。案例是 Bcan 0.0.8b 對 Super A'Can
`$F001F0`（pixel mode／gfx mode）的處理，結果見
[f003-video-mode.md](f003-video-mode.md) §7；本文只談方法。

## 1. 問題的形狀決定方法

「Bcan 有沒有用 bit 3」不能用搜尋命中數回答。命中數會隨編碼形式改變：同一個欄位可以被
byte 讀、被 word 讀後移位、被 8-byte 一次載入後只取其中兩格，也可以先複製到另一個結構
再由別的函式讀。**要回答的是資料流：值從哪裡進來、被搬到哪、最後誰讀它。**

因此方法的骨架不是「全域搜尋這個位址」，而是**沿著程式自己的結構走**：

1. 找一個可靠的錨點。字串是最好的錨點，因為它把「人看得懂的功能」與「程式位址」綁在一起。
   本案用截圖功能的錯誤訊息（`aperture`、`320x240`）找到 `sub_140048500`。
2. 從錨點往內走一層，看它把工作交給誰：`sub_140048E40`（取視訊 snapshot）。
3. 再往內：`sub_140082130` 建 snapshot、`sub_14009D6E0` 是真正的 renderer。
4. 到這裡才開始問「那個欄位在 snapshot 的哪個位移」，並且**只在這條鏈上**驗證。

順序反過來（先全域搜尋、再猜結構）會讓每一次搜尋的空命中都被讀成「沒有人用」。

## 2. 陷阱一：掃描範圍與程式的存取形式不匹配

第一版做法是掃「對視訊物件欄位的直接結構位移存取」，例如 `[reg+252h]`。結論是
「renderer 沒有讀 pixel mode」。這個結論自洽，但錯。

**偵測手段是正對照**：挑一個「不可能不被用到」的欄位一起掃。tilemap base、sprite base
這些欄位 renderer 一定要用；結果它們同樣掃不到。這代表**不是那些欄位沒被用，而是這個掃描
看不見 renderer 的存取方式**——它讀的是每幀複製出來的 snapshot，不是原物件。

> 規則：任何「掃不到 ⇒ 沒有人用」的推論，都必須先讓一個已知會被使用的目標通過同一個掃描。
> 正對照失敗時，要修正的是方法，不是結論。

這與 `~/diagnosis-notes/docs/02-query-returned-empty/` 的「查詢回空要先做正對照」是同一件
事，只是這裡的「查詢」是反組譯掃描。

## 3. 陷阱二：把反編譯器的巨集當成位元組佈局

第二版做法讀到 snapshot 建構器的偽碼：

```c
v2 = *(_QWORD *)(a2 + 168740);     // video+588..595
*(_WORD *)(a1 + 188) = v2;
*(_WORD *)(a1 + 190) = HIWORD(v2);
```

`HIWORD(x)` 在 Hex-Rays 的定義是 `(x >> 16) & 0xFFFF`，於是我把 `snapshot+190` 讀成
`video+590..591`，據此推論兩個 mode byte（在 `video+594/595`）根本沒進 snapshot。同樣自洽，
同樣錯。

反組譯的事實是：

```
140082132: mov  rax, [rdx+29324h]     ; video+588..595
1400821D9: mov  [rcx+0BCh], ax        ; snapshot+188 = video+588
1400821E0: mov  r8, rax
1400821E3: shr  r8, 30h               ; >> 48
1400821E7: mov  [rcx+0BEh], r8w       ; snapshot+190 = byte 6、+191 = byte 7
```

`shr r8,48` 之後再取低 16 位，取的是 byte 6–7，正是兩個 mode byte。偽碼把「先位移、再取
低半字」渲染成 `HIWORD`，讀者若把巨集當成固定的 byte lane 就會偏移四個 byte。

> 規則：偽碼負責提供假設，反組譯負責提供事實。**凡是結論依賴「某欄位落在哪個 byte」，
> 一律回到指令層確認一次。** 這一步成本只有幾秒鐘。

## 4. 陷阱三：過濾規則本身引入盲區

第三版做法為了排除堆疊變數的雜訊，把運算元字串含 `sp`／`bp` 的一律略過。這在多數 x64
程式成立，但 MinGW／gcc 產生的這支程式把 `rbp` 當一般基底暫存器用來指向 snapshot：

```
14009F422: movzx eax, byte ptr [rbp+0BFh]     ; gfx mode，被過濾掉了
14009FA8D: movzx eax, byte ptr [rcx+0BEh]     ; pixel mode，留下來了
```

於是同一輪掃描裡，一個欄位「有人讀」、另一個「沒人讀」，而差別只是基底暫存器的名字。

> 規則：**過濾規則要能說出自己濾掉了什麼。** 若說不出來，就不要過濾——寧可拿到雜訊再人工
> 判讀。本案最後改用不過濾的全 `.text` 枚舉，結果是每個欄位各一個讀取點，乾淨且可複述。

順帶一提，掃描範圍也要注意：以 `get_func(ea)` 的 `start_ea`／`end_ea` 當邊界，遇到有 tail
chunk 的函式會漏掉一部分。全區段枚舉沒有這個問題。

## 5. 可重用的檢查清單

下次要回答「X 有沒有被消費」時，依序做：

1. **先寫下「如果結論是錯的，錯誤會長什麼樣」**。本案的答案是「值其實是先被複製到別的結構
   才被讀」——寫下來之後，第 2 步就會自然想到要驗證有沒有中間結構。
2. **從字串或已知功能錨點沿呼叫鏈往下**，不要從全域搜尋開始。
3. **每個掃描配一個正對照**：挑一個必定會被使用的同類目標一起掃。
4. **偽碼只當線索，位址與位元組佈局回到反組譯確認**。
5. **過濾條件要能解釋盲區**；不確定就不要過濾。
6. **枚舉整個 `.text`，不要只掃一支函式**。
7. **把「找不到」與「我的方法看不到」分開寫**：前者是結論，後者是待辦。

## 6. 本案最後得到的鏈

```text
$F001F0 寫入
  → sub_1400A9200：拆成 video+594 (value & 0x18) 與 video+595 (value & 7)
  → sub_140082130：mov rax,[video+588]；shr rax,48；存到 snapshot+190/+191
  → sub_14009D6E0：
        14009F422 讀 snapshot+191 → gfx mode → 三張圖層 region 表 → bpp
        14009FA8D 讀 snapshot+190 → pixel mode==8 且 ROZ 為 8bpp 時走另一套 ROZ 路徑
```

三次錯誤結論分別是：renderer 不讀（範圍錯）、兩個 byte 沒進 snapshot（byte lane 錯）、
gfx mode 沒被使用（過濾錯）。三次的共同點是**每一次都自洽、都能寫成看起來嚴謹的段落**，
而且只有在下一輪引入新的驗證手段時才會暴露。這就是為什麼「證據等級」與「方法限制」要跟
結論寫在一起：讀者得看得出這個結論是被什麼方法支撐的，才知道它可能在哪裡失效。
